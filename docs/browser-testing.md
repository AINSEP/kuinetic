# Browser testing

Why this exists, how to run it, and — the part that was missing before this doc — how an agent
should actually use the output to diagnose a failure.

> **Rerun this after any change to `src/`:**
>
> ```sh
> npm run test:browser
> ```
>
> This is a real, git-committed regression suite (`test/browser/`, not gitignored), not a one-off
> script. One command runs all six suites end-to-end and prints a pass/fail summary; nothing about
> it needs to be remembered or reconstructed. If a future fix lands for either defect in
> `docs/browser-findings.md`, this is the command that confirms it — the two currently-failing
> checks named there should flip to `PASS`, and every other check should stay green throughout.

## Why a browser harness at all

The unit suite (`npm test`) runs in jsdom. jsdom never evaluates `@keyframes`, never applies
`animation-timeline`, never runs `requestAnimationFrame` against real layout, and reports zero for
every `getBoundingClientRect()`. Everything this library promises — that a paused animation
genuinely holds its from-state, that a FLIP reorder computes the right inverse transform, that a
real mouse drag produces real pointer events a recogniser can see — is unproven by that suite. Six
real defects have been caught only by driving an actual Chromium (see `docs/HANDOFF.md`).

There are two browser-driven layers, and they answer different questions:

| Layer | Command | Question it answers |
|---|---|---|
| `scripts/verify-browser.mjs` | `npm run verify:browser` | Do the 24 baseline claims about CSS effects, activation, composition, and parameters still hold? |
| `test/browser/*.test.mjs` | `npm run test:browser` | Do the specific behaviors the external review flagged as unproven (nested scroll coordinates, FLIP geometry, multi-subpath SVG, real pointer gestures, reduced-motion gating, post-destroy cleanliness) actually hold? |

**`verify:browser` is a canonical gate** — it must be green alongside `npm test`, `eslint`, and
`tsc` before any handoff claims "done". **`test:browser` is diagnostic, not a gate.** Some of its
checks are defect-finding by design and are *expected* to fail until a Programmer with `src/` in
scope fixes the underlying source — see `docs/browser-findings.md` for which ones and why. Do not
treat a `test:browser` failure as a broken test without first checking whether it's a known,
recorded finding.

## Running it

```sh
npm run verify:browser        # 24 baseline checks, fast, no artifacts
npm run record                 # same 24 checks, plus video + a named PNG filmstrip
npm run test:browser           # the six test/browser/ suites, always captures named frames
```

All three run `npm run build` first (an esbuild bundle of `src/` into `demo/kuinetic.js` /
`.css`), since every fixture — `demo/index.html` and everything under `test/browser/fixtures/` —
loads the library from that compiled bundle, not from TypeScript source directly.

Chromium is resolved by `scripts/browser-harness.mjs`'s `loadChromium()`: it tries
`playwright-core`, then `playwright`, then an explicit `PLAYWRIGHT_MODULE` path. `playwright-core`
is pinned to exactly `1.61.1` in `package.json` — do not widen that range without also downloading
a matching Chromium build; a newer minor version has demanded one before.

## Where evidence lands

```
.artifacts/
├── video/*.webm                        — from `npm run record` only; continuous, human-watchable
└── frames/
    ├── verify-browser/NN-<check-name>.png   — from `npm run record` only
    ├── scroll-nested/NN-<name>.png          — from every `npm run test:browser` run
    ├── flip-geometry/NN-<name>.png
    ├── svg-morph-subpath/NN-<name>.png
    ├── gestures/NN-<name>.png
    ├── reduced-motion/NN-<name>.png
    └── destroy-cleanup/NN-<name>.png
```

Frames are numbered in call order within their suite (`01-`, `02-`, ...) and named after the check
or moment they document. `.artifacts/` is gitignored — it is regenerated by running the scripts,
never committed.

## How to actually use this as an agent

**A video cannot be read as an image; a PNG can.** That distinction is the entire reason the named
filmstrip exists. If you are diagnosing a browser-test failure, do not try to open or reason about
a `.webm` file — go straight to the numbered PNG for the check that failed.

Concretely: `npm run test:browser` prints, on failure, a line like

```
- [svg-morph-subpath] morph output preserves both subpath boundaries (M count)  expected 2 "M" commands, found 1 — d=M15,15 C...
```

The `[suite]` prefix names the directory: `Read .artifacts/frames/svg-morph-subpath/02-morphed-output.png`
to see the actual rendered shape, not just the `d` string in the failure message. For this specific
finding, the frame shows a visible dark wedge cutting from the square's corner into its hole —
confirming with your own eyes that the two subpaths were joined by a spurious connecting segment,
rather than trusting the printed coordinates alone. `docs/browser-findings.md` already did this
cross-check for the two known findings; do the same for any new failure before assuming it's a
regression.

For a suite that passed, the frames are still useful as a "what does correct look like" reference —
e.g. `.artifacts/frames/gestures/06-drag-settled.png` shows a plain drag resting exactly where it
was released, which is the visual you'd compare a future regression against.

**Continuous motion is burst-sampled, not just before/after.** FLIP, spring physics, and gesture
drags are inherently continuous — a single before/after frame pair proves the endpoints but not
that the path between them was correct (no wrong overshoot, no jank, no broken intermediate
geometry). `flip-geometry` and `gestures` sample several points across the actual transition
(`scripts/browser-harness.mjs`'s `burstSample()`) instead of one midpoint, so their frame
directories contain a real filmstrip you can flip through in order —
e.g. `.artifacts/frames/gestures/11..18-elastic-spring-return-*-of-8-at-*pct.png` is the spring
return's actual settle curve, eight frames across its 800ms window. Discrete state claims (opacity
reveals, ARIA attributes, parameter overrides) don't need this — they're single facts, not motion.

## Suite contract, if you're adding a new one

Every file in `test/browser/*.test.mjs` exports:

```js
export const name = 'my-suite'                          // used for the frame subdirectory and log prefix
export async function run({ browser, ARTIFACT_DIR }) {  // one Playwright Browser, shared across suites
  const { check, results } = createChecker()             // from scripts/browser-harness.mjs
  const snap = createFrameRecorder(`${ARTIFACT_DIR}/frames/${name}`)
  // ... open your own context/page, assert, snap(page, 'moment-name') at each meaningful state ...
  return results                                          // { name, passed, detail }[]
}
```

`scripts/run-browser-tests.mjs` discovers every `test/browser/*.test.mjs` file, launches one shared
Chromium instance, runs each suite's `run()` in file-name order, and aggregates pass/fail into a
single exit code. Fixtures live in `test/browser/fixtures/*.html` and load the library via a
relative path to the compiled `demo/kuinetic.js`/`.css` — build fresh, self-contained HTML
files with deterministic geometry (fixed pixel sizes, no external network dependency) rather than
reusing `demo/showcase/*.html`, which references remote `picsum.photos` images and is not
deterministic enough for pixel-level assertions.

If a suite is defect-finding rather than a regression guard, say so in its top-of-file comment (see
`test/browser/svg-morph-subpath.test.mjs` and `test/browser/gestures.test.mjs` for the pattern) so
a future run of `npm run test:browser` doesn't read an expected failure as newly broken.
